# Architectural Anti-Patterns & Prohibited Practices

## 1. Overview
This document catalogs prohibited architectural antipatterns within the `EricksonLopez.Mediator` ecosystem to guarantee Native AOT safety, CQRS purity, and sub-nanosecond dispatch latencies.

---

## 2. Prohibited Antipatterns

### AP-01: Runtime Assembly Scanning (`AddMediatR`-style reflection)
- **Antipattern:** Calling `Assembly.GetTypes()` at application startup to register message handlers.
- **Why Forbidden:** Scanning assemblies at startup creates cold-start latency spikes (100ms - 500ms) and fails unpredictably under Native AOT due to IL trimming.
- **Enforcement:** Compile-time static handler discovery generated by Roslyn.

### AP-02: Delegate-Based Pipeline Execution (`RequestHandlerDelegate<T>`)
- **Antipattern:** Allocating `Func<Task<TResponse>>` closures per middleware behavior.
- **Why Forbidden:** Allocating closure objects on every in-process request creates continuous GC Gen 0 pressure.
- **Enforcement:** Struct-based `INext<TResponse>` continuations.

### AP-03: Dual Command / Query Roles in a Single Message
- **Antipattern:** Mutating database state while simultaneously returning large domain entities from a query.
- **Why Forbidden:** Violates CQRS semantic separation.
- **Enforcement:** Strict interface contracts: `ICommand<TResponse>` vs `IQuery<TResponse>`.

### AP-04: Polymorphic Reflection-Based Dispatch
- **Antipattern:** Invoking mediator handlers via `dynamic` or `MethodInfo.Invoke`.
- **Why Forbidden:** Breaks trimming analysis and leads to crashes in published AOT binaries.
- **Enforcement:** Strongly-typed static dispatch tables.
